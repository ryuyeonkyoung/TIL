# 에러 핸들러 (Error Handler)

## Custom Exception Class
- 비즈니스 상황에 맞는 예외를 직접 정의하는 클래스

### Custom Exception Class vs ControllerAdvice
- 예외를 발생시키는 역할 → Custom Exception Class
- 예외를 받아서 처리하는 역할 → ControllerAdvice
- 특정 상황에서 의도적으로 예외를 발생시키고, 예외 처리 로직에서 구분할 수 있게 함
- 일반 예외로 선언할 경우 **Exception**, 실행 예외로 선언할 경우 **RuntimeException**을 상속받아 구현

---

## RestControllerAdvice
- @ControllerAdvice 기능에 @ResponseBody가 결합된 형태
- 모든 @ExceptionHandler 메서드의 반환값을 JSON/XML 등 HTTP 응답 본문으로 자동 직렬화

### (Rest)ControllerAdvice의 장점
- 하나의 클래스에서 모든 컨트롤러에 대해 **전역적으로 예외 처리** 가능
- **직접 정의한 에러 응답**을 일관성 있게 클라이언트에 내려줄 수 있음
- 별도의 try-catch문 없이 **코드의 가독성**이 높아짐

### (Rest)Controller가 없을 때 불편한 점
1. 비즈니스 로직과 예외 처리 코드 혼재
2. 중복된 예외 처리 코드
3. 에러 응답 포맷 불일치
4. 유지보수의 어려움

### (Rest)ControllerAdvice 사용 시 주의점
- 한 프로젝트당 하나의 ControllerAdvice만 관리하는 것이 좋음
- 여러 ControllerAdvice가 필요하다면 basePackages나 annotations 등으로 구분
- 직접 구현한 Exception 클래스들은 한 공간에서 관리

---

## 예시 코드
```java
@RestControllerAdvice
public class GlobalRestExceptionHandler {

    // 특정 예외 처리: 리소스 없음
    @ExceptionHandler(ResourceNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)
    public ErrorResponse handleNotFound(ResourceNotFoundException ex) {
        return new ErrorResponse(
            ex.getMessage(),
            HttpStatus.NOT_FOUND.value(),
            LocalDateTime.now()
        );
    }

    // 모든 예외 처리: 서버 에러
    @ExceptionHandler(Exception.class)
    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    public ErrorResponse handleAll(Exception ex) {
        return new ErrorResponse(
            "서버 내부 오류가 발생했습니다.",
            HttpStatus.INTERNAL_SERVER_ERROR.value(),
            LocalDateTime.now()
        );
    }
}

// 에러 응답 DTO
@Getter
@AllArgsConstructor
public class ErrorResponse {
    private String message;
    private int status;
    private LocalDateTime timestamp;
}
```

## Global Exception Handler
- @RestControllerAdvice가 붙는 클래스
- 애플리케이션 전체에서 발생하는 예외를 한 곳에서 처리하는 클래스
- 하나의 GlobalExceptionHandler 클래스로 모든 컨트롤러에 대해 전역적으로 예외처리를 할 수 있음
- 예외 발생 시 일관된 에러 응답을 반환하고, 필요하면 슬랙/디스코드 등 웹훅을 통해 알림도 가능

## Converter
- 서비스/컨트롤러에서 사용할 데이터 객체를 변환
- 웹에서는 기본적으로 문자열을 통해 데이터가 전달되는데, 다른 타입으로 변환

### Converter의 구조
```java
public interface Converter<S, T> {
    T convert(S source);
}
```

- S: 원본 타입
- T: 변환할 타입

### ConversionService
- Converter를 모아 관리하고, 실제 변환을 수행

### 활용
- 커스텀 객체 변환, Enum 변환, 복잡한 파라미터 변환 등에 자주 사용

### Converter vs Mapper
→ Converter은 타입 변환, Mapper은 객체 간 데이터 매핑

| **구분** | **언제 사용?** | **대표 예시** |
| --- | --- | --- |
| Converter | 단순 변환 | String ↔ Enum, String ↔ LocalDate, 코드 ↔ Enum |
| Mapper | 매핑 방식 | Entity ↔ DTO, DTO ↔ VO, 복잡한 객체 변환 |

속도 비교

| **구분** | **변환 대상** | **변환 방식** | **성능 특징** |
| --- | --- | --- | --- |
| Converter | 단일 값/타입 | 단순 파싱/변환 | 매우 빠름, 오버헤드 거의 없음 |
| Mapper | 객체 ↔ 객체 | 수동/자동 매핑 | 매핑 방식에 따라 차이 있음 |
|  |  | (리플렉션/코드생성) | 리플렉션 기반은 느릴 수 있음 |

[참고: Spring Converter Javadoc](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/core/convert/converter/Converter.html)

## lombok
- 자바 프로젝트를 진행하는데 거의 필수적으로 필요한 메서드/생성자 등을 **자동 생성**해 줌으로써 반복적인 **보일러플레이트 코드를 줄이는 데 도움**을 줘서 코드를 절약할 수 있도록 도와주는 라이브러리

### spring annotation vs lombok annotation
- 롬복 어노테이션: **컴파일 시점**에 동작, 코드 생성을 자동화 하는 데 사용한다.
    - @Getter, @Setter, @RequiredArgsConstructor
- 스프링 어노테이션: **런타임 시점**에 동작, 의존성주입/설정/AOP 등을 처리한다.
    - @Autowired, @Component

### Lombok의 장점
- 어노테이션 기반의 코드 자동 생성을 통한 생산성 향상
- 반복되는 코드 다이어트를 통한 가독성 및 유지보수성 향상
- Getter, Setter 외에 빌더 패턴이나 로그 생성 등 다양한 방면으로 활용 가능

### Lombok의 주요 어노테이션
| **어노테이션** | **설명** |
| --- | --- |
| @Getter | 모든 필드에 대한 getter 생성 |
| @Setter | 모든 필드에 대한 setter 생성 |
| @ToString | toString() 메서드 생성 |
| @EqualsAndHashCode | equals(), hashCode() 메서드 생성 |
| @NoArgsConstructor | 파라미터 없는 생성자 생성 |
| @AllArgsConstructor | 모든 필드를 파라미터로 받는 생성자 생성 |
| @RequiredArgsConstructor | final, @NonNull 필드만 파라미터로 받는 생성자 생성 |
| @Data | @Getter, @Setter, @ToString, @EqualsAndHashCode, @RequiredArgsConstructor를 합친 것 |
| @Builder | 빌더 패턴 생성 |
| @Slf4j | SLF4J 로깅 객체 자동 생성 |
| @SneakyThrows | 예외 처리(try-catch/throws) 없이 예외를 던질 수 있게 함 |
| @Value | 불변(immutable) 클래스 생성 |

→ 객체의 불변성을 지키기 위해 @Setter의 사용은 크게 권장되지 않는다.

## 정답
1. **일관된 예외 처리**: 스프링의 기본 예외 처리 방식을 확장하여 모든 컨트롤러에서 일관된 응답 포맷을 제공
    - **코드 중복 방지**: 공통 예외 처리 로직을 한 곳에서 관리하여 중복 코드를 제거
    - **유지보수 용이**: 예외 처리 로직을 분리해 핵심 비즈니스 코드를 간결하게 유지

2. `@ControllerAdvice` 또는 `@RestControllerAdvice`에 여러 속성을 사용해 스코프를 제한한다.
    1. basePackages,annotations, assignableTypes
    2. 여러 속성을 동시에 지정하면 OR 조건(하나라도 해당되면 적용)

    ```java
    @ControllerAdvice(assignableTypes = {TargetController.class})
    public class CustomExceptionAdvice1 {
        // 특정 클래스(컨트롤러)에만 적용
    }
    
    @ControllerAdvice(basePackages = "com.example.api")
    public class CustomExceptionAdvice2 {
        // 특정 패키지에만 적용
    }
    
    @ControllerAdvice(annotations = RestController.class)
    public class CustomExceptionAdvice4 {
        // 특정 애노테이션이 붙은 컨트롤러에만 적용
    }
    
    @ControllerAdvice("com.example.api")
    public class CustomExceptionAdvice5 {
        // 예외 처리 메서드
    }
    
    ```

3. @Order 어노테이션을 통해 우선순위를 지정한다. 숫자가 낮을수록 먼저 적용된다.

    ```java
    @ControllerAdvice
    @Order(1)  // 숫자가 낮을수록 높은 우선순위
    public class HighPriorityAdvice { ... }
    ```

4. **`@ResponseBody` 추가 필요**: **`ResponseEntity`** 대신 DTO를 반환할 때는 반드시 **`@ResponseBody`**를 클래스 또는 메서드에 추가해야 함.

  스프링이 내부적으로 `handleExceptionInternal()`을 호출할 때 HTTP 상태 코드를 설정하지 못할 수 있으므로 `@ResponseStatus`를 함께 지정하거나 `ResponseEntity<?>`로 래핑해야 한다.

5. 메소드 파라미터에 선언된 예외 타입을 자동으로 인식하여 처리

  예) `public void handler(NullPointerException ex)` → `NullPointerException` 전용

6. **비동기 처리**: **`@Async`**를 사용해 웹훅 전송 로직을 별도 스레드에서 실행
    - **큐 활용**: RabbitMQ, Kafka 등을 통해 이벤트를 큐에 저장하고 순차적으로 처리
    - **재시도 메커니즘**: Spring Retry를 사용해 일시적 오류 시 재시도

    ```java
    @Retryable(maxAttempts = 3, backoff = @Backoff(delay = 1000))
    public void sendWebhook() { ... }
    ```
